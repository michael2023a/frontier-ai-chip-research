## §0 先纠正命题：这一层不是"提速"，是**采购决策权**

开题时我给自己定的问题是"硬件之外那 40% 的性能从哪来"。检索完 12 次后我认为**这个问题问窄了**，它预设软件是硬件的附属增益项。实际证据指向一个更强的命题：

> **软件栈这一层的经济作用，是把"买什么芯片"这个决策权从芯片厂商手里拿回来。**

三条证据链：

**① 合池部署 = 只能买 GPU。** B6 已证明 prefill 与 decode 的最优硬件**不同**（prefill 算力受限 → 配给 argmax(FLOP/s per \$)；decode 带宽受限 → 配给 argmax(bytes/s per \$)；两条成本曲线**反向**——H100 prefill 比 A100 便宜 1/3，但 decode 比 A100 **贵** 1/5）。可只要你把两个阶段放在**同一个池**里跑，你就只能买"两件事都还行"的硬件——那恰好就是 GPU 的定义。

> **推论：CUDA 护城河真正的来源不是算子生态，是"合池部署"这个默认形态本身。** 只要不解耦，替代方案在物理上就没有插槽。

**② 解耦一旦成立，插槽就出现了。** 解耦后 prefill 池与 decode 池可以分别采购。decode 池不需要完整 CUDA 栈——它只需要能接收 KV 缓存、能跑 attention。**这是 TPU / Trainium / SN50 / LPU 唯一不需要十年生态积累就能进场的通道。**

**③ 而插槽的控制权在传输层。** vLLM、SGLang、TensorRT-LLM **三家默认集成的都是 NVIDIA 的 NIXL**。Google 2026 年开源 TPU Raiden（Apache-2.0，SemiAnalysis 首先标记），定位**与 NIXL 同一层**，且文档自己写明"仍在积极开发中，**尚未面向通用生产用途**"【一手三方·SemiAnalysis/Google 仓库文档】。

**→ §0 结论（本层主命题）：NVIDIA 的护城河不是消失了，是上移了——从"写算子"（CUDA）上移到"搬 KV"（NIXL）。** 与 `B1` 的"每 GW 打包值"是同一件事的两个观测面：前者是**它卖给你的东西更贵了**，后者是**你自己接东西进来更难了**。

**护城河三个落点的时间序列（B1 + B8 合并）**：

| 时期 | 落点 | 机制 | 状态 |
|---|---|---|---|
| 2015–2023 | CUDA 算子生态 | 你写的 kernel 只能在它上面跑 | 仍在，但被 ROCm 追到 feature parity（`B1`） |
| 2024–2026 | 每 GW 打包值 | Hopper $18B → Blackwell $25B → Rubin $40B/GW；网络占 DC 收入 ~12%→~20% | **正在起作用** |
| 2026– | **KV 传输层的默认实现**（NIXL） | 不解耦就没有插槽；解耦就要过这一层 | **刚成型，是当下最活跃的战场** |

## §1 栈的四层分解：价值在上移

| 层 | 代表 | 收益量级（实测） | 成熟度 | **控制方** | 这一层的性质 |
|---|---|---|---|---|---|
| **引擎层** | vLLM / SGLang / TensorRT-LLM / LMDeploy | 彼此差距 **≤10–17%** | 商品化 | 开源社区（vLLM 事实标准） | **已无超额收益** |
| **编排层** | NVIDIA Dynamo / llm-d / Mooncake Conductor | **+30% ~ 2×** 每 GPU；TTFT **2–3×** | 2026 年规模化 | NVIDIA vs Red Hat+Google+IBM 联盟 | **收益/成本比最高** |
| **传输层** | NIXL vs TPU Raiden | 决定上面两层**能不能跨芯片** | NIXL 生产级；Raiden 未投产 | **NVIDIA（当前）** | **咽喉** |
| **缓存层** | LMCache / Mooncake Store / CXL / TurboQuant | 相对全量重算 **1.0×→1.86×**；KV 体积 **−6×** | 快速演进 | 开源 + 内存厂商 | **直接改变 HBM 需求（见 §5）** |

**本层最重要的结构性观察：价值从引擎层上移到了编排层。**
2026 年选引擎不再由吞吐决定（差距已被压到 10% 量级），而由**特性**（SGLang RadixAttention 在共享前缀负载上翻倍）和**运维成本**（TensorRT-LLM 首次编译 ~30 分钟、换模型需重编译 5–60 分钟）决定。→ **引擎已商品化，战场在它上面那一层。**

### 2.2 生态位已经重新划分

## §3 编排层

### 3.1 ★ 命题纠正：vLLM 官方明说——解耦**不提升吞吐**

这是我在这一轮里被纠正的最重要一条，也是全文件最该记住的一条。

> **vLLM 文档直白陈述：解耦式 prefill 不提升吞吐（throughput），它的目的是延迟控制（latency control）——把 TTFT 与 ITL 的调优解耦。**【官方·vLLM 文档】

那么生产里那些 +75%、+525% 的吞吐数字从哪来？答案是：**它们来自"整套解耦栈"，不是来自"打开解耦开关"。**

> **整套解耦栈 = 解耦 + 专家并行（EP/DP 重新配置）+ 大批次 + prefix 缓存 + 缓存感知路由。**
> 单独打开 vanilla vLLM 的 disaggregated prefill 开关，吞吐不动。

**证据（DeepSeek 是最干净的样本）**：解耦后 prefill 与 decode 可以采用**完全不同**的并行度——prefill 用较小的 EP/DP（4 节点，Routed Expert EP32/DP32，每 GPU 管 9 个路由专家 + 1 个共享专家），decode 用**极宽**的 EP144/DP144（18 节点，每 GPU 管 2 个路由专家 + 1 个共享专家），从而把 GroupGEMM 利用率拉满。**这个收益只有解耦后才可能出现，但它不是"解耦"本身，是"解耦解锁的并行度重配"。**
→ **prefill:decode 节点比 = 4:18**（每节点 8×H800，即 32 GPU : 144 GPU）【一手·DeepSeek 2025-02 披露】

**→ 方法论结论（可复用到其他子课题）：看到"某技术带来 X% 提升"时，先问"是开关还是栈"。** 这条与 `B4` 的"宣布 ≠ 开工"、`B6` 的"合同 ≠ 收入"是同一类错误。

### 3.2 ★ 解耦的四个阈值（缺一即亏）

| 阈值 | 数值 | 不满足时 | 来源 |
|---|---|---|---|
| **模型尺寸** | 必须够大 | **小模型解耦反而更慢** | Massed Compute 2026-08-31 自测：2×RTX PRO 6000 Blackwell + **Qwen3-0.6B**，解耦 TTFT **18.7ms vs 聚合 12.3ms**；8 路 92 tok/s vs 145 tok/s。原因：**NIXL 传输开销相对计算量占比过大**【一手三方·厂商自测】 |
| **Prompt 长度** | 经验值 **8,000+ token** | prefill 不够重，没有可隔离的干扰 | 多方一致的工程经验值【产业媒体·particula】 |
| **并发与规模** | **高且持续**；规模上约 **16–32 张 GPU** | 低并发时没有"正在进行中的 decode"需要保护 | `B6` 已载；particula 并列 |
| **互连带宽** | **必须 RDMA**（IB/RoCE）；**TCP 不是"降级方案"，是不成立** | 3 GB/s 时传输成本超过它要省下的工作 | codesparring 的 KV 传输-重算对比模型 |

**一个漂亮的物理边界（传输 vs 重算）**：
> 传输优于重算的条件**与 prompt 长度无关**——只取决于互连带宽是否超过一个由"模型每 token KV 字节数 × decode GPU 算力 ÷ 参数量"决定的固定阈值。参考模型在 A100 decode 池上该阈值约 **10 GB/s**。**任何现代背板都远超此值**，所以真实 GPU 集群上"传输 vs 重算"这个决策几乎总是选传输；只有边缘场景或广域链路才会反转。【一手三方·The Machine Learning Society 成本模型】

**传输开销的量级**：Splitwise 按层流水发送（每层 KV 一产出就开始传），**实测开销 <7%**；不可重叠的常数部分约 **A100 8ms / H100 5ms**（InfiniBand）。【一手三方·Splitwise】

**TaiChi 的边界更精确**：
- **TTFT 紧、TPOT 松 → 聚合胜**（合池可以在 prompt 一到就整批做 prefill）
- **TPOT 紧、TTFT 松 → 解耦胜**（decode 池永不被打断）
- **两者都紧 → 两者都不最优，正确答案是混合**

### 3.4 KV-aware 路由：收益/成本比最高的一层

**几乎是零硬件成本，却是全栈收益最大的单点。**

- **Dynamo KV-aware 智能路由**：10 万条**真实** DeepSeek R1 查询（ISL 4k / OSL 800）在 H100 上 → **TTFT 约 3× 更好、平均延迟约 2× 更低**【官方·NVIDIA，测试条件披露完整，可信度高】
- **llm-d 智能路由 vs 轮询**：输出吞吐 ~3×、TTFT ~2×【一手三方·Red Hat】
- **跨模型路由（`B6` 已载）**：某客户把简单查询从 70B 改路由到 7B → **\$0.70 → \$0.12/千补全（−83%）**；路由开销 5ms，省下 40ms 生成延迟

> **为什么路由的杠杆这么大？** 因为它把"用哪个模型、走哪张卡、命中哪份缓存"从**部署时决策**变成**运行时决策**。它是全栈唯一能跨芯片、跨模型起作用的优化，也是唯一不需要改硬件的一层。

**→ 路由层是 B1/B2/B6 三线硬件竞争的"上层裁判"**：它决定一张卡实际被分到多少工作。**NVIDIA 之外的硅能不能拿到 decode 池的份额，不看它多快，看路由层愿不愿意把活派给它。**

### 3.5 SLO 编排：延迟分级 = 收入侧工具

llm-d 明确按延迟容忍度划分 QoS 谱系【一手三方·Red Hat】：

| 等级 | 场景 | 容忍度 |
|---|---|---|
| O(ms) | 代码补全、搜索响应 | 人在环路内 |
| O(秒) | 对话 agent、邮件起草 | 交互 |
| O(分钟) | 视频/邮件摘要、deep research | 容忍 |
| O(小时) | 夜间批处理、会议纪要、自主 agent | 无感 |

> **这条的价值不在技术，在商业**：**同一批 GPU 可以按延迟等级分层定价。** 软件栈因此不只是成本侧工具，它直接改变了收入侧——这与 `A1b` 的单位经济模型是同一条线。
> Dynamo SLO Planner 实测：基线方案的 SLA 违例多 **80%**，Dynamo **TCO 低 5%**【官方·NVIDIA，待第三方】。

**Mooncake 的"预测式早拒"是最激进的一条**：调度器若预测某请求无论如何都满足不了 SLO，就在 prefill **之前**直接拒绝，而不是烧掉一次昂贵的 prefill 再失败。**这意味着"接受一部分请求不服务"被写成了系统设计的前提。** 这是吞吐与 SLO 之间的一次明确取舍，值得单列。

## §4 传输层：护城河的新落点（NIXL vs Raiden）

| | **NIXL**（NVIDIA） | **TPU Raiden**（Google） |
|---|---|---|
| 定位 | 推理传输引擎，Dynamo 的组成部分 | **与 NIXL 同一层**（SemiAnalysis 判定） |
| 覆盖范围 | RDMA / NVMe / **对象存储（S3）**，单一 API 跨 GPU/CPU/存储 | 单机器内 chip-to-chip、跨 VM 走网络、TPU 内存 → host RAM 卸载 |
| 生态位 | **vLLM 的默认选项**；SGLang / TensorRT-LLM / LMDeploy 均已集成 | 尚待 vLLM/SGLang 集成 |
| 成熟度 | 生产级 | **Google 文档自述"仍在积极开发，尚未面向通用生产用途"** |
| 独有设计 | — | **共享内存模式：模型服务器重启时 KV 缓存仍在 DRAM 中保留**，用于生产环境例行二进制更新不产生冷启动 |

**Google 为什么现在放出来？** 因为它必须。TPU 客户已经外溢——Anthropic 锁定 **100 万颗 TPU**、OpenAI 也开始用 Google TPU 跑部分业务。**每一个这样的客户都需要 TPU 的软件生态成熟到能跑生产级解耦推理，否则他们就得回到 NVIDIA。** 而 vLLM/SGLang 都已经深度接入 NIXL。
→ **Raiden 是 TPU 外售战略的必要补丁，不是技术展示。** 这也从反面确认了 §0 的命题：**传输层就是插槽的控制权。**

**NVIDIA 的另一手**：2026-08-04 宣布把 **cuFile API 与存储栈**开放给一个跨厂商 GitHub 组织，初始维护者包括 **Google、Intel、Meta**。→ 这是"开放以巩固默认地位"的经典动作：**把传输层的邻接层标准化，同时保持核心（NIXL）在自己手里。**

**→ 与 `B2` 的接口**：B2 已判 **TorchTPU 2026-10 开源是 ASIC 侧最关键的单一节点**。B8 的判断是：**TorchTPU 解决的是"模型能不能在 TPU 上跑"，Raiden/NIXL 解决的是"TPU 能不能被接进解耦集群"——这是两个不同的门，前者开了不等于后者开。**
**→ 与 `B6` 的接口**：B6 已判推理专用硅**只能当 decode 池的协处理器**。那么它**进入市场的唯一通道就是传输层**。Sohu / LPU / SN40 要么被 NIXL 接纳，要么自建连接器。**B6 里所有公司的商业前景，实际上都挂在 B8 这一节的结论上。**

## §5 缓存层：KV 外移 = HBM 瓶颈的**需求侧**出口

> **这一节是 B8 与 B3 的新接缝，也是我发现的第二个跨线冲突。**

### 5.1 分级卸载的实测（最干净的一组真实负载数据）

Xinnor 用 vLLM + Mooncake + xiRAID Opus 跑**真实 agentic 负载**，以"全量重算 = 1.00×"归一化【一手三方·Xinnor】：

| 配置 | 相对全量重算 |
|---|---|
| 仅 vLLM 本地前缀缓存 | **1.04×** |
| 仅 RAM 存储 | **1.10×** |
| RAM + 本地 NVMe RAID0 | **1.52×** |
| RAM + **远端 NVMe-oF** | **1.52×**（与本地持平——**共享不额外花钱**） |
| xiRAID Opus + GDS（**不用 RAM 层**） | **1.86×** |

**两条被忽略的结论**：
1. **"远端 = 本地"**：KV 缓存走 NVMe-oF 共享出去，性能不掉。**意味着缓存可以跨节点池化，而池化不损失收益**——这正是 Mooncake Store 的设计前提，现在有了独立实测。
2. **"这一层的价值由每张 GPU 上跑的会话数决定，不是由 GPU 利用率决定。"**（原文：the tier's value is decided by sessions per GPU, not GPU utilisation）→ **缓存层的收益是复用率的函数，不是算力的函数。** 这跟 §2 的"软件收益是并发的函数"是同一个规律。
3. **运维陷阱**：一次 lease-TTL 配置错误**吃掉了约一半的收益**——这一层的收益高度依赖调参，不是开箱即得。

LMCache 的分层（Apache-2.0，11k+ stars，已被 llm-d 采用为 KV 卸载后端）【一手三方】：
- **L0** GPU HBM / **L1** CPU DRAM（10–50ms）/ **L2** NVMe RAID-0（50–200ms）/ **L3** Redis-Valkey
- 256-token 块、**bit-exact 重载**（不损失精度）、CacheBlend 支持**非前缀复用**
- AMD MI300X agentic 基准：32 并发 / 100K 上下文下 **TTFT 低 3.0×**
- arXiv 2510.09665 声称多轮 QA **最高 15×** ⚠ **论文自报，量级远高于上面实测的 1.86×——并列，不取舍**

### 5.2 CXL：把这一层硬件化

| 证据 | 结果 | 分级 |
|---|---|---|
| **Samsung CXL 内存池研究（2026-07）** | CMM-D 模块 + CXL 交换机，前端接 NVIDIA Blackwell，跨 **8 张 GPU** 承载 KV 缓存 → 达到 **DRAM 性能的约 92%**，且容量远超主机 DRAM；纯 DRAM 基线在缓存超出容量后断崖（需付重算代价） | 【一手三方】 |
| **TraCT（Virginia Tech，2026-06）** | 用 CXL 共享内存替代 RDMA 做 KV 传输（P/D 解耦机架级）：**TTFT 降低最高 2.6×、P99 延迟降 3.0×、峰值 goodput 高 1.9×**（对比 RDMA 基线），真实多轮对话负载 | 【一手三方·学位论文，真实 CXL 硬件】 |
| **SK hynix ITME 架构** | CXL 混合内存置于 HBM/DDR 与存储之间，推理吞吐 **最高 +35.7%** | 【厂商自报】 |
| **浪潮 MantaKV（2026-03）** | CXL 池化共享内存集中存 P 节点产生的 KV，D 节点**直接读取无需二次传输**，且天然成为全局持久缓存（无需卸载到本地 SSD）——**把两次搬运合并为一次写入** | 【厂商自报·中国】 |
| **北大 + 阿里云（2026-03）** | CXL 内存池存 Engram，集成进 SGLang，**端到端性能接近本地 DRAM** | 【一手三方·中国】 |
| **Penguin Solutions MemoryAI** | GTC 2026 发布基于 CXL 的 KV 缓存服务器 | 【官方·产品发布】 |
| **Meta Vistara** | **ISCA 2026 一手论文**：数百万台服务器生产部署，解耦式 ML 推理服务器 **−25%**、分布式缓存延迟 **−29%**、OOM **−33%**；**代价必须并列**：CXL 挂 DDR4 带宽约为本地 DDR5 的 **1/10**、延迟 **+60%**（详见 `C1` §3.3） | 【一手·ISCA 2026；2026-10-15 由 `C1-CXL与UMA.md` 回写，本条待验证结案】 |

**TraCT 的意义值得单独说**：它证明了**解耦的传输不一定要走网络**。如果 CXL 能跨机架，KV 传输的成本从"网络协议栈"降为"load/store"——**这会同时削弱 NIXL 的地位**（§4 的咽喉可能另有出口）。**这是目前唯一有可能绕开 NVIDIA 传输层控制的技术路径，值得持续跟踪。**

### 5.3 压缩：同样的目标，纯算法路线

**Google TurboQuant**（arXiv 2504.19874，ICLR 2026）【一手三方·论文】：
- 两阶段：**PolarQuant**（随机旋转 → 每坐标标量量化）+ **1-bit QJL**（修正内积估计偏差）
- **3.5 bit/channel 质量中性**；2.5 bit 有边际退化；**KV 内存降低 ≥6×**；**attention logit 计算最高 8× 加速**（H100，4-bit 模式，对比 JAX FP32 基线）
- LongBench（Llama-3.1-8B）：TurboQuant 3.5-bit **50.06** = FP16 **50.06**；2.5-bit 49.44；KIVI 3-bit 48.50
- Needle-in-a-Haystack（4× 压缩）：TurboQuant **0.997** = FP16 0.997；KIVI 0.981；PolarQuant 0.995；SnapKV 0.858
- 失真率距信息论下界仅约 **2.7 倍**；**data-oblivious——无需校准、无需重训**

**并列的三条反证**（必须并列）：
1. **Google 未开源官方实现**（社区已有 Triton / MLX / llama.cpp 实现）
2. **论文全部测试模型仅到约 8B**——70B/405B 上是否成立**未验证**，而那才是 KV 缓存真正成为瓶颈的量级
3. **Two Minute Papers 的独立复核**：现实收益更接近 **30–40%**，而非 6×；"不是每台机器突然只需要 1/6 内存，那有点理想化"
4. **NVIDIA 的竞品 KVTC**：**20× 压缩但需 per-model 校准**——两者不是同一产品（免校准 vs 极致压缩）

### 5.4 ★ 与 B3 的新冲突：HBM 瓶颈可能不是被产能解决，而是被软件绕过去

`B3` 判定 2027 年瓶颈是 **HBM/DRAM**。`B6` 已给出**供给侧**的例外条款（Cerebras / Taalas 不用 HBM）。B8 现在给出**需求侧**的第二条：

> **KV 缓存外移（DRAM/NVMe/CXL）+ 压缩（3.5 bit ≈ 1/6），从需求侧直接削减 HBM 用量。**
> 量级：DeepSeek 生产实测 **56.3% 的输入 token 命中盘上 KV 缓存**——这意味着**超过一半的 prefill 算力与 HBM 容量需求被存储层吸收掉了**。

**→ 这个发现的双向含义（必须同时写，不能只写一面）**：
- **对 B3**：HBM 需求曲线可能比线性外推更平。**B3 的"2027 卡 HBM"结论需要补注一个需求侧的缓冲项。**
- **对 B6（潜在冲突，新发现）**：B6 把"不用 HBM"列为 Cerebras/Taalas 的**可得性优势**。但如果软件能把 HBM 需求普遍削减数倍，那么**所有架构都变得不那么依赖 HBM，B6 那条优势会被稀释**。→ **B6 的"绕开供应链"护城河，有效期可能取决于软件栈的进展速度。这是一个此前没有人指出的耦合。**

## §6 单卡内的三个杠杆：全部是**并发的函数**

### 6.1 连续批处理与 PagedAttention

| 机制 | 收益 | 测试条件 | 分级 |
|---|---|---|---|
| **PagedAttention** | 显存浪费从 **60–80% 降到接近 0**；同等延迟下 **2–4×** | SOSP 2023 / arXiv 2309.06180 | 【一手三方·Berkeley】 |
| **连续批处理** | Orca 报告 **36.9×**（同等延迟下）；Anyscale/vLLM 实测 **23×** | 同上负载假设不同 → **并列** | 【一手三方】 |
| **vLLM vs Ollama（按并发）** | 并发 1 → **1.2×**；并发 8 → **10×**；并发 32 → **16×**；并发 128 → **19×** | 同上 | 【产业媒体】 |

> **★ 这是本层最反直觉、也最有用的一条：连续批处理在单用户下几乎没有收益（1.2×），在 128 并发下是 19×。**
> **软件栈的收益不是常数，是并发的函数。**
> → 这直接解释了为什么 `B1`（NVIDIA 护城河）、`B2`（自研 ASIC 划算）、`B6`（推理专用硅有市场）三条线**都在说"规模是入场券"**——**不是巧合，是同一个物理事实的三个投影。**
> → **推论（三线闭环）**：软件栈收益随规模增长 → 只有超大规模玩家拿得到它 → 而只有拿到它才值得自研 ASIC（B2）→ 而 ASIC 又要求你已有解耦栈才插得进去（B6）→ 而解耦栈的接口由 NVIDIA 控制（B8）。**四者互相锁定，形成闭环。这个闭环本身就是最深的护城河，也是唯一可能被打破的地方——如果传输层被标准化（CXL 或跨厂商组织）。**

> **单张 H100 + 投机解码 ≥ 两张 H100 + NIM → GPU 成本降 50%。**
> 这不是"快了多少"，是"**你可以少买一半卡**"。这是把投机解码从技术指标翻译成资本开支指标的少数公开案例。

3. **输出分布完全不变**（拒绝采样保证），所以这是**无损**优化——与量化不同，量化是用精度换速度

## §8 与其他线的接缝与冲突（B8 的输出）

### 8.1 对 `B1`（护城河）
- **新增第三个落点：KV 传输层的默认实现（NIXL）**。时间序列：CUDA 算子 → 每 GW 打包值 → NIXL。
- **新增机制解释**：CUDA 护城河的真正来源不是算子生态，是**"合池部署"这个默认形态本身**——不解耦就没有替代方案的插槽。
- **规模特权（与 B1 同源）**：软件收益是并发的函数（1.2×→19×），只有超大规模拿得到。

### 8.2 对 `B2`（云厂 ASIC）
- **两个门，不是一个**：TorchTPU 解决"模型能不能跑"，Raiden/NIXL 解决"能不能被接进解耦集群"。**B2 把 TorchTPU 列为最关键的单一节点，B8 认为还得加一个传输层节点。**
- **Google 开源 Raiden 是 TPU 外售战略的必要补丁**（Anthropic 100 万颗 TPU、OpenAI 部分业务上 TPU）——从反面确认传输层是咽喉。
- **AWS × llm-d 的意义**：AWS 选择的是"在 llm-d 里塞 EFA + libfabric + NIXL"，**而不是自建传输层**。→ **AWS 接受了 NVIDIA 的传输层标准，只在底下换芯片。** 这是"传输层即咽喉"最硬的一条证据。

### 8.3 对 `B3`（上游/HBM）—— **新冲突**
- **需求侧出口**：KV 外移 + 压缩（3.5 bit）从需求侧削减 HBM。DeepSeek 生产实测 **56.3% 输入 token 命中盘上 KV**。
- **B3 需补注**：2027 年 HBM 瓶颈的结论需加一个需求侧缓冲项。
- **CXL 值得 B3 关注**：Samsung 92% DRAM 性能、TraCT 2.6×/1.9×——如果 CXL 跨机架成熟，它可能同时改变"HBM 需求"与"传输层控制权"两件事。

### 8.4 对 `B6`（推理专用硅）—— **双向，且含一个此前未指出的耦合**
- **正向**：解耦是 B6 所有公司**唯一的市场准入通道**（B6 已判它们只能做 decode 池协处理器）。
- **反向（新发现）**：B6 把"不用 HBM"列为可得性优势；若软件把 HBM 需求普遍削减数倍，**这条优势会被稀释**。→ **B6 的护城河有效期取决于 B8 的进展速度。**
- **同源的规模门槛**：解耦要 16–32 卡 + 8k+ prompt + RDMA + 大模型，与 B6 的"只有超大规模部署才有意义"完全同构。

### 8.5 对 `A1b` / `A-2`
- **收入侧接口**：SLO 编排把同一批 GPU 按延迟等级分层售卖（O(ms) → O(小时)），直接改变单位经济模型。
- **一个待查的周期冲突**：`A-2` 判模型能力**每 3 个月翻倍**；而本层任何一项优化从发布到生产可用（Dynamo GA、llm-d v0.7、Raiden 未投产）都在**季度级**。**若模型迭代快于软件栈落地，软件栈永远在追一个移动靶。** 这与 `B6`×`A-2` 的冲突（模型迭代 vs 硅片冻结）是同一族问题，只是时间常数不同（硅片 ~2 个月定制周期，软件 ~1 个季度）。

### 8.5.1 ★★ 与本节结论的正面冲突（2026-10-12 由 `AB-交汇·模型与硅.md` 追加）：OpenAI 在 Jalapeño 上**不做** prefill-decode 解耦

**本节把解耦写成"有四个阈值的最佳实践"。`AB` 检索到一个明确的反例，而且反方的理由很硬。**

【一手三方·SemiAnalysis 转述 OpenAI 的决策】OpenAI 在其自研推理芯片 **Jalapeño** 上**没有采用 PDD**，SemiAnalysis 表示意外（"NVIDIA 与 AMD GPU 即便在同构硬件上也从 PDD 获益显著"）。理由原文：

> "**当 workload 被冻结时，PDD 看起来很划算**……**但生产流量不会停在这个比例上。** 输入与输出序列长度、并发、缓存命中率、投机接受率、延迟目标全天都在动。
> **一旦把设备分成 prefill 池与 decode 池：prefill 需求过多 → decode 芯片闲置而请求排队；decode 需求过多则相反。** 运营方必须持续预测正确的切分、两边都预留冗余、并不断再平衡一个理想比例永远在移动的系统。
> **在统一系统里，某些资源可能在某个阶段被低用，但每台设备都能服务下一个请求。在解耦系统里，整颗芯片可能仅仅因为属于错误的池而闲置。局部利用率看起来更好，全局利用率可能很差。**"
> **且：解耦还会破坏局部性（locality）。**

**这不是"谁对谁错"，是两个不同的优化目标，必须并列：**

| | 本节的解耦派 | OpenAI 的统一派 |
|---|---|---|
| 硬件前提 | 同构 GPU 机队，跨机架 RDMA | **Jalapeño 局部域 128 XPU / 27.5 TB HBM4，KV cache 常驻域内** |
| 优化目标 | **延迟可控**（vLLM 官方：解耦**不提升吞吐**） | **全局利用率**（避免整芯片因"属于错误的池"而闲置） |
| 流量假设 | 可切分、比例相对稳定 | **生产流量比例全天在动** |
| 关键代价 | 需持续预测切分 + 双边冗余 + 再平衡 | 单阶段内可能有资源低用 |

**→ ★ 对本节结论的修正：解耦不是普适最佳实践，而是「局部域规模 + KV 能否留在域内」的函数。**
- **局部域足够大且 KV 能常驻域内**（Jalapeño 128 XPU / 27.5 TB；或 `B5` 的 Google OCS 9,216 芯片）→ **统一池更优**（局部性保住了，切分问题消失了）；
- **局部域小、KV 必须跨机架搬运** → 解耦才划算（把搬运变成可控的批量传输）。

**→ 因此 §3 的四个阈值要加第五个条件：局部域规模。** 而这个变量恰好由 `B5` 度量——**`B5` 反复强调"分界线是域大小而不是技术偏好"，本节与之完全咬合。**

⚠ 并列 OpenAI 自己的 caveat：初始基准是单轮 8k/1k 且**未启用 MTP**，长上下文、多轮、agentic 负载下结论仍开放。

**另附 `AB` 给本节补上的一个机制性修正**：**本节把"软件栈"当一层谈收益，`AB` §4.2 说明它内部要再分——算子层（已被 TileLang/CANN 基本解决：DeepGEMM-Ascend 达硬件上限 99.8%）与系统层（通信/调度/并行策略/故障恢复，仍是主要损失来源，全链路效率仅海外 55–65%）。** → 已固化为第六类口径错误「**算子 ≠ 系统**」。

### 8.6 ★ 独立验证（2026-10-12 由 `B7-国产替代.md` 追加）：软件栈是「有效算力乘数」，不是竞争力之一

**本层此前的结论都是"软件栈决定收益"。`B7` 用一个完全独立的数据源（中国国产替代场景）给出了同样的结论，而且量级可以量化。**

**★ 决定性证据：同一个机房里的对照实验**【一手三方·证券时报调研，南方某国家级智算中心】：
> 装 NVIDIA GPU 的服务器机柜，**出租率 90% 以上**；装国产 GPU 的服务器，**价格便宜很多，出租率不到 50%**。询问缘由，机房负责人回答：**"机效差距很大，尤其在生态上。"**

**这不是性能差距，是软件栈差距——因为价格已经便宜很多了，客户仍然不选。**

| 国产侧的软件栈损耗 | 数字 | 来源 |
|---|---|---|
| 全链路国产 vs 海外的**训练效率比** | 同等十万卡规模、千亿参数离线训练：海外约 **12 天**，全链路国产 **18–21 天** → **有效算力产出仅 55–65%** | 某国产 AI 芯片厂商商务负责人（匿名） |
| **国产芯片平均闲置率** | 40 多个算力中心**平均约 60%**，**个别超 80%** | GACS 2026 会议纪要 |
| **国产异构算力池利用率** | 某园区综合利用率约三成，其中**国产异构算力池全年平均利用率不到两成**；原因：**多厂商混部在调度层未统一纳管，客户模型迁移需逐一适配驱动与算子库** | 现场调研 |
| **利用率梯度** | 头部云厂商专属集群 **75–98%**；省会中型 **25–40%**；三四线千卡级 **10–22%** | 宇量整理 |
| **★ 正面证据（瓶颈可解）** | 陕西某国企算力项目：初期自有团队对昇腾底层算法库与推理框架熟悉度不足，利用率一度很低；**引入华为昇腾技术团队驻场做全链路调优后，利用率攀升至 80–90%** | 深澜智算创始人 |

> **→ 结论：在国产替代场景里，软件栈不是"竞争力之一"，是"有效算力乘数"。**
> **→ 且解药形态很关键：是"厂商驻场"，不是"多买卡"。**这意味着国产替代的成本结构里有一笔**英伟达体系不需要付的人力成本**——本层此前从未把"人力调优"计入 TCO。

**★ "多对多"问题：国产特有的组合爆炸**【GPUStack CTO 梁胜】：
> "根本上需要解决**多对多**的问题——上面有多个模型，下面有多个 GPU。"

模型、芯片、推理引擎（vLLM / SGLang / TensorRT-LLM / MindIE）持续增加，组合数随之爆炸，靠项目团队逐个适配的成本越来越高。**这是本层"迁移成本"在中国被放大的结构性原因：美国是 1 个硬件栈 × N 个模型，中国是 M 个硬件栈 × N 个模型。**

**★ 一条可能产出硬数字的线索**：**中国信通院 2025 年已启动"DeepSeek 国产化适配测评"**，测评项除"能否跑起来"外，还包括**工具链易用性、适配成本、功能完备性、性能表现**。**这是目前最可能把"迁移成本"变成可引用数字的地方，建议持续跟踪其测评结果发布。**

**CANN 侧的进展（正面）**：KADC 2026（2026-05-22）全面开源——**50+ 仓库、800+ 算子、Triton 100% 兼容（600+ ops）、TileLang 100% 兼容（300+ ops）、PyTorch 2,300+ APIs 对齐**；DeepSeek V4 系列 **day-zero 昇腾支持，新模型迁移到适配最短 6 小时**；DeepSeek 2026-09-30 开源把整个 CUDA 工具链（TileLang、HPC 库、分布式通信库）移植到昇腾；面壁智能 BitCPM-CANN 适配+优化约 **3 周**。
⚠ **生态差距仍在**：CUDA 400 万+ 开发者 vs CANN；大规模训练仍有约 **15–25%** 开销。

### 8.7 一条元观察
> 这一层用到的几乎**全是旧计算机科学**：分页、引用计数、写时复制、缓存层次、把活派给已经有数据的那台机器、网络对象存储。**"这是一个操作系统课程 + 一个分布式系统课程，指向了一个新问题。"**
> → **推论：软件栈这一层没有算法护城河，只有工程护城河。** 对比 `B6` 的 Etched（硬化 Transformer 架构 = 下注未来），软件栈是**不下注、纯工程**。所以**这一层不会出现赢家通吃的技术，但会出现"默认实现"的通吃**（NIXL 就是这样成为默认的）。

## §11 B8 已确立的结论（供 `00` 回写）

1. **★ 本层主命题不是"软件能提速多少"，是：软件栈把"买什么芯片"的决策权从芯片厂商手里拿回来。** 合池部署 = 只能买 GPU；解耦后出现 decode 池插槽；插槽控制权在传输层（NIXL）。
2. **★ NVIDIA 护城河三段落点**：CUDA 算子生态 → 每 GW 打包值（$18B→$25B→$40B/GW）→ **KV 传输层默认实现（NIXL）**。第三个是 2026 年新增、当下最活跃的战场。
3. **★ 命题纠正：vLLM 官方明说解耦不提升吞吐，只做延迟控制。** 生产里的 +75%/+525% 来自"整套解耦栈"（解耦 + 专家并行重配 + 大批次 + prefix 缓存 + 缓存感知路由），不是来自开关。→ **"开关 ≠ 栈"是本课题第 3 类口径错误。**
4. **★ 解耦有四个阈值，缺一即亏**：模型够大（Qwen3-0.6B 解耦反而慢：18.7ms vs 12.3ms）/ prompt 8k+ / 并发高且持续（16–32 卡）/ 必须 RDMA。**TCP 不是降级方案，是不成立。**
5. **★ 软件收益是并发的函数，不是常数**：连续批处理并发 1 只有 1.2×、并发 128 达 19×；而投机解码相反（batch 4 → 2.3×，batch 32 → 归零）。**两者对并发响应相反，同一集群必须分流。**
6. **★ 厂商/论文/模拟 vs 生产/真实负载，普遍差 2–8 倍**（投机解码 2–4×、Mooncake 7×、TurboQuant 3×、LMCache 8×、Dynamo 4–7×）。**这条换算规律比任何单个数字都值钱。**
7. **★ 与 B3 的新冲突（需求侧）**：KV 外移 + 3.5bit 压缩从需求侧削减 HBM；DeepSeek 生产实测 **56.3% 输入 token 命中盘上 KV**。**B3 的"2027 卡 HBM"需补需求侧缓冲项。**
8. **★ 与 B6 的双向耦合（此前未指出）**：B6 的"不用 HBM = 可得性优势"，有效期取决于 B8 软件栈削减 HBM 需求的进度。**若软件把 HBM 需求普遍削数倍，B6 那条优势被稀释。**
9. **传输层是咽喉，且 AWS 已默认接受**：AWS 在 llm-d 里塞 EFA+libfabric+**NIXL**，而不是自建传输层。Google 开源 Raiden 是对这一点的确认（且自述未投产）。
10. **CXL 是唯一可能绕开 NIXL 的路径**：TraCT 用 CXL 共享内存替代 RDMA，TTFT −2.6×、P99 −3.0×、goodput +1.9×；Samsung 实测 92% DRAM 性能。**若跨机架成熟，会同时改变 HBM 需求与传输层控制权两件事。**
11. **引擎层已商品化**（差距 ≤10–17%），价值上移到编排层。选型由**特性**（SGLang RadixAttention 共享前缀 2×）与**运维成本**（TRT-LLM 换模型需重编译 5–60 分钟）决定。
12. **路由是收益/成本比最高的一层**（近零硬件成本）：Dynamo KV-aware 在 10 万条真实查询上 TTFT ~3×、延迟 ~2×；llm-d ~3×/~2×；跨模型路由 −83% 成本。**路由层是 B1/B2/B6 三线硬件竞争的上层裁判。**
13. **SLO 编排是收入侧工具**：同一批 GPU 按延迟等级（O(ms) → O(小时)）分层售卖。Mooncake 甚至把"预测式早拒"写进设计前提。
14. **元观察**：这一层几乎全是旧计算机科学（分页/引用计数/COW/缓存层次/网络对象存储）→ **没有算法护城河，只有工程护城河与"默认实现"的通吃。**
