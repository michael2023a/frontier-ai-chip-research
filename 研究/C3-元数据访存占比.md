## 〇、为什么开这条线

`AB` 收官时，从**中兴 2026-04 论文**里挖出一个此前没人写下的判断：

> **瓶颈不是被消除，而是被分化。** DeepSeek-V4 的 CSA + HCA + MTP 把原始 KV 换成压缩块，**降低原生 KV 容量，却引入压缩索引 / 块元数据 / 稀疏检索的新开销**；
> **FP4 混合量化成为权重部署主流，group-wise 缩放因子与路由索引的元数据访存占比持续抬升。**
> → **"绕开 HBM" ≠ "绕开内存墙"。**

当时的问题是：**只有定性判断，完全没有量化数据。**
`00` §2 变量 4 那一栏写的是"目前完全没有量化数据，只有中兴论文的定性判断（持续抬升）"。

**本轮要回答三件事**：
1. 这个占比**到底是多少**（能不能算出来）
2. 它**怎么衡量**才是对的
3. 它**在上升吗**，机制是什么

## 一、分析单位（★ 先钉死）

**元数据不是一个东西，是四类来源。每类的量级、位置、代价都不同。**

| # | 来源 | 具体形态 | 住在哪里 |
|---|---|---|---|
| **①** | **量化缩放因子** | MXFP4 的 E8M0（每 32 值 1 字节）／NVFP4 的 FP8 式 scale | 与权重/激活同址，随张量搬 |
| **②** | **MoE 路由索引与门控** | 每 token 的 top-k 专家编号 + 权重；router 权重矩阵 | 显存；决定 All-to-All 模式 |
| **③** | **压缩注意力的块索引** | CSA 压缩条目、HCA 摘要 token、**Lightning Indexer 的 FP4 相关性分数** | **留在 HBM**（这是关键，见 §5） |
| **④** | **混合精度格式标记** | RoPE 维度 BF16 / 其余 FP8；OPAL 的 exception 标记；MX+ 的扩展尾数位 | 与 KV 同址 |

**衡量方式有两层（★ 这是本线对变量 4 定义的修正）**：
- **L1 · 字节占比**：元数据占总访存字节的比例
- **L2 · 撬动量**：元数据**决定**了多少后续数据移动

**→ 只测 L1 会严重低估这个变量。见 §3。**

## 二、★ 第一个可精确计算的基准：MXFP4 的元数据占 5.9%

【一手技术·AMD MI355X / ATOM 部署文档，gfx950 架构】MXFP4 的张量解剖：

| 组成 | 规格 |
|---|---|
| FP4 payload | 2 个 **E2M1** 值打包进 1 个 uint8 字节 |
| E8M0 scales | **每 32 个 K 维原始值 1 个 uint8 scale** |

**算一遍（这是本文件最硬的一个数字）**：

```
32 个原始值 → 16 bytes FP4 payload + 1 byte E8M0 scale = 17 bytes
每原始值      → 17 / 32 = 0.53125 bytes
理论 FP4      → 0.5 bytes/value
```

| 指标 | 数值 |
|---|---|
| **元数据相对 payload** | **+6.25%**（1 / 16） |
| **★ 元数据占总字节** | **1 / 17 ≈ 5.88%** |
| **实际压缩率** | 相对 FP16 不是干净的 4×，而是 **0.53125 B/value → 约 3.0×** |

**第三条来源交叉验证**：【产业媒体】"per-block scale factors add **a few percent** of memory back, so real-world FP4 does not hit a clean 4×" —— 与 5.9% 一致。

**★ 这就是变量 4 的第一个量化基准：`MXFP4 元数据 ≈ 5.9%`。**

**并且它有一个明确的权衡方向**（【一手技术】原话）：
> **"The trade-off between them is precision versus metadata."**
> - **MXFP4**（OCP 标准）：块 32、E8M0 二次幂 scale —— **厂商中立、元数据少**
> - **NVFP4**（NVIDIA）：**更小的块 + FP8 式更高精度 scale** —— **精度更好，元数据更多**

【论文·Meta Platforms，arXiv:2603.08713】给出了这个权衡的硬件代价：
> **MXFP4 相对 NVFP4 有 12% 的 tensor core 相对面积节省。**

**→ 一句话：想要精度就得付更多元数据字节；想要面积/能效就得接受更粗的 scale。这是一条可以量化兑换的曲线。**

### 2.1 ★ 一个关键的硬件设计岔路

【一手技术·gfx950】最重要的机制说明：

> **在 gfx950 上，block scale 不是"反量化前必须消失的查找表"，而是 scaled MFMA 指令（V_MFMA_SCALE_F32_*）操作数流的一部分，与 FP4 payload 一起被消费。**

对比 W4A8：per-group weight scales **装不进 INT8 内层循环**，必须先软件反量化。

**→ 判读：元数据是不是"额外访存"，取决于硬件是否把它纳入指令流。**
**→ 同一个 5.9%，在支持 scaled MFMA 的硬件上是"顺路带上"，在不支持的硬件上是"额外一趟"。**

这一条对 `B6`（近存/存算一体）和 `B7`（国产）都直接有用：**国产卡要跑 MXFP4/MXFP4，必须支持 scaled MFMA 类指令，否则元数据开销会变成实打实的额外访存。**

## 三、★★ 元数据是控制信息，不是数据（本线最重要的判读）

**这是本轮最想说的一句：只看字节占比会严重低估这个变量。**

### 3.1 MoE：2 MB 的索引撬动了 40–50% 的运行时间

| 事实 | 数值 | 来源 |
|---|---|---|
| **路由索引 + 权重的显存占用** | batch 32 × seq 2048，仅**约 2 MB** | 【从业者·CSDN】 |
| **但它决定了 All-to-All 通信模式** | All-to-All 消耗训练与推理**总运行时间的 40–50%** | 【产业媒体·综述】 |
| **通信缓冲区峰值占用** | 生产环境观测到**高达 1.2 GB** | 【从业者·CSDN】 |
| router 权重本身 | d=8192 × E=64 → **524,288 参数**，且**是每 token 必经路径、无法跳过** | 【从业者·CSDN】 |
| 8×H100 实测 | 稠密 Llama3-70B e2e **120 ms** vs MoE 版 P95 **185 ms**；**多出的 65 ms 中 22 ms 花在 PCIe 数据搬运** | 【从业者·CSDN】 |

**→ 2 MB 的元数据，撬动了 GB 级的通信缓冲区和 40–50% 的运行时间。**
**→ 这就是 L1 与 L2 的差距：字节占比 <0.1%，撬动量 >40%。**

### 3.2 压缩注意力：FP4 打分只为选出 Top-512，但它决定了后面读什么

DeepSeek V4 的 CSA 三步（【技术解析·量子位转述】）：

| 步 | 内容 |
|---|---|
| ① KV 压缩 | **每 m=4 个相邻 token 的 KV 条目压成 1 条**（重叠压缩避免块边界截断） |
| ② 稀疏筛选 | **Lightning Indexer 用 FP4 精度快速打出相关性分数**，为每个 query 选出 **Top-512（Flash）/ Top-1024（Pro）** 个压缩条目 |
| ③ 核心注意力 | 只在选中的压缩块上做 Multi-Query Attention |

**→ Lightning Indexer 本身的数据量极小（FP4 分数），但它决定了后面 512/1024 个块要不要被从 HBM/存储里读出来。**

**个人实测（832K token 代码库，vLLM，【待验证】）**：
- 纯 CSA：KV cache 降至原体积 **38%**，但首 token 延迟仍 **1.2 s**
- **加入 HCA 后：cache 降到 9.7%，首 token 延迟降到 0.38 s**（−68%）
- 机制：**HCA 让模型跳过对非关键区域的逐 token 计算**

**★ 结论：变量 4 的定义必须修正——**
> **不能只用"字节占比"衡量，必须加上"它撬动了多少数据移动"。**
> **元数据是控制信息：它自己很轻，但它命令的东西很重。**

## 四、上升的证据链（机制层面，"持续抬升"在这里落地）

中兴论文只说了"持续抬升"。本轮把**为什么会抬升**拆成了五环，每一环都在提高元数据的相对密度：

| 环 | 机制 | 元数据效应 |
|---|---|---|
| **1 · 注意力压缩** | CSA **m=4** → HCA **m'=128**；61 层交替堆叠 + 128 token 滑动窗口 | **压缩率越高，索引/摘要 token 相对原始 KV 的密度越高** |
| **2 · 索引器低精度化** | **Lightning Indexer 内部注意力计算以 FP4 精度执行** | 索引本身变小，但**索引的相对重要性上升**（它现在是唯一的"全量扫描"环节） |
| **3 · HCA token 极端量化** | **HCA token 的 key/value 被强制量化到 4 bit，只存储梯度更新所需的最小必要信息** | HCA token 已从"数据"退化为**纯元数据**（存在性标记） |
| **4 · KV 混合存储格式** | **RoPE 维度保持 BF16，其余维度用 FP8** → KV 容量再压缩近半 | **格式标记/非对齐访问成为新的访存开销来源** |
| **5 · 权重低精度化** | FP4/MXFP4 成为权重部署主流 | **每 32 值 1 字节 scale（5.9%）成为常驻项** |

**→ 五环叠加的结果：数据在被压缩，元数据在被保留甚至强化。**
**→ 这就是"内存墙被挪位、未被拆除"的具体机制。**

**量化效果（并列，不换算）**：
- 1M 上下文下：**FLOPs 降至 V3.2 的 27%、KV Cache 降至 10%**
- 对比 **BF16 GQA-8 标准基线：KV Cache 只剩约 2%**
- CSA + HCA 整体：**1M 上下文 KV-cache 使用量减少 90%**

## 五、★ DeepSeek V4 = 这个问题的极端答案：HBM 正在变成"索引层"

【产业媒体·VentureBeat，引 DeepSeek V4 架构论文 + 硬件建模基准测算】

| 模型 | 1M 上下文所需 HBM |
|---|---|
| **DeepSeek V4-Pro（1.6T MoE）** | **5.48 GB** |
| GLM5 | 60 GB |
| Qwen3-235B-A22B（GQA 标准） | **89 GB** |
| GPT-5.5 / Claude 4.7 级（西方前沿 MoE） | **180+ GB** |

**★ 机制（本节核心）**——MLA 的"物理分工"：

> **GPU 上只保留极小的、高度压缩的搜索索引标签（Keys）；**
> **把重的数据载荷（Values）整个卸载到更便宜的系统内存与本地存储层。**
> **GPU 先做高速匹配找到相关数据，再按需从存储里把 Values 调出来。**

**→ 这不就是"元数据留在快层、数据下沉到慢层"吗。**
**→ 换句话说：HBM 的角色正在从"数据层"变成"索引层"。**

**★ 与 `C1` 的完美衔接**：
| | C1 的三条路线 | C3 的 DeepSeek 路线 |
|---|---|---|
| 落点 | KV 中间层（NVIDIA 叫 G3.5、华为叫 L3.5） | **Values 下沉到系统内存 / SSD / NAND / LPDDR** |
| 留在 HBM 的 | 最热的实时推理数据 | **压缩索引（Keys）+ 元数据** |
| 介质 | DDR / flash | **国产 NAND flash、消费级 SSD、LPDDR（长江存储、长鑫）** |

**→ 两条完全独立的路径指向同一个结构：HBM 变小、变贵、变"索引专用"；KV 的真正数据体量沉到便宜介质。**
**→ 这正是 `B3`"HBM 是 2027 最硬瓶颈"的需求侧缓冲机制——不是少买 HBM，是 HBM 里装的东西变了。**

**地缘含义（VentureBeat 判读）**：把 HBM 需求压到 5.48 GB，使前沿 AI 可以跑在**不受出口管制的国产存储层**上。

**成本兑现**：
- V4-Pro API 永久降价 75%，输入 **0.025 元/百万 token**，输出 6 元
- GPT-5.5 输出 **$30/百万 token**（约 216 元）
- **1M 超长上下文推理成本仅为 GPT-5.5 的 1/70**
- 腾讯云随后下调 V4 系列价格，最高降幅 **97.5%**，缓存命中价降至 0.000025 元/千 tokens

【官方·DeepSeek 技术报告】细粒度 EP 方案在 **NVIDIA GPU 与华为昇腾 NPU 两个平台**上验证：

- 延迟敏感场景最高 **1.96×**
- **这是 DeepSeek 首次把国产芯片与 NVIDIA GPU 并列写入硬件验证清单，确立对等地位**

**Day-0 适配**：V4 发布当日，**华为昇腾、寒武纪、海光、摩尔线程、沐曦、昆仑芯、平头哥真武、天数智芯 8 家国产 AI 芯片 + 英伟达**同时宣布完成适配——**大模型产业首次实现 Day-0 级全栈适配**。

### 6.2 ★ 缺口仍在，且与上面的响应不是同一件事

【中兴 2026-04 论文】指出的现存短板：
1. 软件栈与编译器支持不足
2. 低精度量化误差控制
3. MoE 路由预测不确定性
4. **★ 压缩注意力索引检索的硬件加速缺失**

**→ 裁决**：华为昇腾 950PR 做的是 **"数值格式的硬件加速"**（MXFP8/MXFP4 原生支持、融合 kernel 降低访存）；
中兴论文说的是 **"索引检索的硬件加速"**（压缩块的选择/检索本身没有专用硬件）。
**这两件事不在同一层，不矛盾，但后者目前无人做。**

**→ 这是本线给出的第二个可操作结论：`B6`（近存/存算一体）与 `B7`（国产替代）都应该把"压缩注意力索引检索的硬件加速"列为空白机会点。**

### 6.3 软件侧的补丁与其代价

【论文·Meta，arXiv:2603.08713】两个纯软件技术：
- **OAS（Overflow-Aware Scaling）**：在二次幂块缩放下扩大有效动态范围
- **MBS（Macro Block Scaling）**：以更粗粒度分配更高精度缩放，更好保留 outlier

| 效果 | 数值 |
|---|---|
| MXFP4 与 NVFP4 的端到端精度差距 | **约 10% → 低于 1%** |
| **代价** | **GEMM 开销 6.2%（平均）** |
| 保留的收益 | MXFP4 的硬件效率优势（**tensor core 面积节省 12%**） |

**其他精度/元数据权衡点**：
- MXFP4 无微调精度掉 **5–30%**；MXFP8 <0.1–0.5%；MXINT8 <0.2%
- **MX+**：复用 outlier 的指数位做扩展尾数 → zero-shot 准确率相对 vanilla MXFP4 **+42%**，代价 **+0.25 bits/element 存储**
- **OPAL**：每块把最大的 n 个值标记为 "exception" 用更高精度编码

**→ 一条清晰的兑换曲线：精度 ↔ 元数据字节 ↔ GEMM 开销 ↔ 硬件面积。四个量可以互相换，不能同时最优。**

## 八、尚未解决 / 待验证（9 项）

1. **MXFP4 的 5.9% 是静态存储占比，不是动态访存占比** —— 实际访存中 scale 的读取次数可能与 payload 不同（scale 可能被缓存、被复用）。**需要区分"存储占比"与"访存占比"，目前只有前者。**
2. **NVFP4 的元数据占比** —— 已知"块更小、scale 精度更高"，但**没有具体字节数**。这是与 MXFP4 对比的关键缺失。
3. **MXFP4 在不支持 scaled MFMA 的硬件上的实际额外访存** —— gfx950 的"顺路带上"是特例，通用情况未知。
4. **其他三类的量化数据完全为零** —— MoE 路由索引、压缩注意力块索引、混合精度格式标记的**字节占比与访存占比都没有数字**。目前只有 MoE 的"约 2 MB"这一个从业者口径。
5. **"撬动量"如何标准化测量** —— 本线提出了 L2 这个概念，但**没有公认的度量方法**（All-to-All 占比 40–50% 是间接证据，不是 L2 的直接测量）。
6. **中兴 2026-04 论文原文** —— 本轮全部经 `AB` 转述引用，**未拿到一手**。
7. **DeepSeek 5.48 GB 数字的来源** —— 是"分析师用硬件建模基准测算"（VentureBeat 语），**非官方发布值**。⚠ 且 KV 降至"10%"与"约 2%"两个口径并存（前者对 V3.2，后者对 BF16 GQA-8 基线）。
8. **832K token 个人实测**（纯 CSA 38% / +HCA 9.7%，TTFT 1.2 s → 0.38 s）—— 单一个人来源，未复现。
9. **昇腾 950PR "融合 kernel + 多流并行降低混合注意力访存开销"的具体幅度** —— 官方未给数字。

## 九、结论（12 条）

1. **★ 变量 4 的第一个量化基准拿到了：MXFP4 的元数据占总字节约 5.9%**（32 值块 = 16 B payload + 1 B E8M0 scale = 0.53125 B/value）。实际压缩率因此是约 3.0× 而非干净的 4×。
2. **★ 这不是"几个百分点"的模糊说法，是能算出来的确定数。** 第三条独立来源（"a few percent"）与之一致。
3. **存在一条可量化兑换的曲线：精度 ↔ 元数据字节 ↔ GEMM 开销 ↔ 硬件面积。** NVFP4 块更小、scale 更精细 → 精度好、元数据多；MXFP4 → 元数据少、**tensor core 面积节省 12%**。
4. **★ 元数据的代价取决于硬件设计**：在 gfx950 上 block scale 是 **scaled MFMA 指令操作数流的一部分**（顺路带上）；在不支持的硬件上是**额外一趟访存**。→ **国产卡要跑 MXFP4，必须支持 scaled MFMA 类指令。**
5. **★★ 元数据是控制信息，不是数据——只看字节占比会严重低估它。** MoE 路由索引只有**约 2 MB**，却决定 All-to-All 通信模式，而 **All-to-All 消耗 40–50% 的总运行时间**；生产环境通信缓冲区峰值达 **1.2 GB**。
6. **★ 变量 4 的定义必须修正：按两层衡量——L1 字节占比 + L2 撬动量。** 只测 L1 会得出"元数据不重要"的错误结论。
7. **压缩注意力的索引同理**：Lightning Indexer 用 FP4 打分只为选出 **Top-512/1024**，但它决定后面哪些块要被读。实测加 HCA 后 KV 从 38% 降到 9.7%、**TTFT 从 1.2 s 降到 0.38 s**。
8. **★ 上升的机制已拆成五环**（中兴论文只给了定性判断）：注意力压缩 m=4→m'=128 ／ 索引器 FP4 化 ／ HCA token 强制 4 bit（已退化为纯元数据）／ KV 混合存储格式（RoPE BF16 + 其余 FP8）／ 权重 FP4 化。**数据在被压缩，元数据在被保留甚至强化。**
9. **★★ DeepSeek V4 是这个问题的极端答案：把元数据（压缩索引、Keys）留在 HBM（仅 5.48 GB），把数据（Values）整个卸载到系统内存/SSD。→ HBM 正在从"数据层"变成"索引层"。**
10. **★ 与 `C1` 完美衔接**：C1 的三条路线把 KV 搬到 G3.5/L3.5 中间层，C3 说明 HBM 里留下的是索引。**两条独立路径指向同一结构。** → **`B3` 的 HBM 需求模型要加"单位 HBM 承载的 token 数"，而不是只看容量。**
11. **硬件侧的响应与缺口不在同一层**：昇腾 950PR 做的是**数值格式的硬件加速**（MXFP8/MXFP4 原生支持 + 融合 kernel）；中兴论文指出的缺口是**压缩注意力索引检索的硬件加速缺失**——**后者目前无人做，是 `B6`/`B7` 的空白机会点。**
12. **成本兑现是真的**：1M 上下文推理成本降至 **GPT-5.5 的 1/70**；V4-Pro 输入 0.025 元/百万 token。**DeepSeek 首次把昇腾与 NVIDIA 并列写入硬件验证清单，且 8 家国产芯片实现 Day-0 适配。**
