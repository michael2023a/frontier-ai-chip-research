**推理专用硅（2026-09-18 由 B6 更新）**
- **核心判断：推理专用硅永远当不了主机，只能当协处理器。** 正确位置是 **decode 池**，prefill 池永远需要 GPU 的 FLOPS
- **「25% LPU 容量」= prefill/decode 解聚的最优资源配比**（不是商业妥协）。依据：每百万 decode token 成本约为 prefill 的 **10 倍**；且 Prefill 成本 H100 < A100，Decode 成本 H100 > A100——**两条曲线反向**
- **推论（重要）**：推理专用硅的真正对手**不是最新 GPU，是上一代退役 GPU**——decode 看"每美元带宽"，而带宽代际提升远慢于算力。**每代退役 NVIDIA GPU 涌入推理市场 = 推理专用硅的价格天花板**
- **适用边界一句话**：**有人在场等待 → 延迟优先；没人在等 → 吞吐优先**

**第五类性质不同**：前四类是把未发生的当成已发生，第五类是**把已发生的当成已生效**——最难从数字表面看出来的一类。
**第六类的含义**：**软件栈不能当一层谈收益，要再分为「算子层」与「系统层」。** 算子层 2026 已基本还清（TileLang 一码四后端、CANN 对 Triton/TileLang 100% 兼容）；**系统层（通信/调度/内存层次/并行策略/故障恢复）才是主要损失来源**。→ 这也解释了 B7 的"解药是厂商驻场"：**驻场调的不是算子，是系统。**
**第七类的含义**：**规范编号描述的是能力上界，不是部署状态。** 它与第五类同类（都是"把已存在的当成已生效"），但更隐蔽——**规范版本号是公开的、可查的、看起来很硬的数字**（4.0 / 128 GT/s / 4,096 节点），极容易被当成部署进度。

**C 线 · CXL 与统一内存（2026-10-12 由 `C1-CXL与UMA.md` 建立）**
- **★ 唯一的生产级大规模落地是资本套利，不是性能故事**：Meta Vistara（ISCA 2026）已**在数百万台服务器生产部署**，解耦式 ML 推理服务器 **−25%**、分布式缓存延迟 **−29%**、OOM **−33%**；Meta 约 **40%** 集群有容量限制。
- **★ 代价必须并列：CXL 挂的 DDR4 带宽约为本地 DDR5 的 1/10、延迟 +60%。** Meta 自研而非买现成的原因（论文原话）：商用方案「把 DRAM 与控制器绑死、不支持 DDR4、功耗与成本不合算」。
- **经济引擎**：服务器刷新 **4–5 年** vs DDR 寿命 **10–12 年**，DDR4 换代时还剩约一半寿命；**DDR5 涨价改变了"直接加 DDR5 更便宜"的算式**。
- **★ 5.5× 的机制是"恢复批大小"不是"更快"**（NELSSA，SK hynix × KAIST，MICRO 2026，真实硬件 + Mooncake trace）：长上下文占满 HBM → 批大小塌到 1 → 队头阻塞。**→ 变量②利用率的收益，与 AB 的 MTP 21× 同类。**
- **★ 同一函数两段**：8B + 4K + 单轮 decode（真实 CXL 测试台）测得 KV 放 CXL 与放 DDR5 **吞吐完全一致（Δ≤0.5%）**；128K+ 混合长度测得 **5.5×**。
- **CXL 带宽 512 GB/s ≠ UALink 800 GB/s ≠ NVLink 5 1,800 GB/s**，不是一个量级；CXL 优势是延迟低（200–500 ns）、一致性、可池化。**"CXL 替代 HBM" 不成立**，共识分层是 HBM（热）+ 本地 DDR5（温）+ CXL 池（大容量）。
- **★ NVIDIA 同时站在 CXL 两侧**：CXL 联盟主席 Derek Rohde 是 **NVIDIA 首席工程师**；NVLink-C2C 官方支持 CXL；Vera 支持 CXL 3.1；2025-09 收购 Enfabrica——**但域内用 NVLink 6 + CMX（以太网+NVMe+DPU），不用 CXL**。**判读：不反对 CXL 做域外/CPU 侧标准，拒绝它做 scale-up 域内的内存层。**
- **★ G3.5 = L3.5**：NVIDIA 与华为各自独立把 KV 中间层命名为 "3.5 层"，都强调"复用而不重算"——**该 tier 客观存在的最硬证据**。

**C3 · 元数据访存占比（2026-10-12 建立，变量 4）**
- **★ 首个量化基准：MXFP4 元数据占总字节约 5.9%**（32 值块 = 16 B payload + 1 B E8M0 scale = **0.53125 B/value**；相对 payload **+6.25%**）→ 实际压缩率约 **3.0×** 而非干净 4×。
- **★ 元数据是控制信息不是数据**：MoE 路由索引 + 权重仅**约 2 MB**，却决定 All-to-All 通信模式，而 **All-to-All 占总运行时间 40–50%**；通信缓冲区峰值 **1.2 GB**。**→ 变量 4 定义修正：L1 字节占比 + L2 撬动量。**
- **代价取决于硬件**：gfx950 上 block scale 是 **scaled MFMA 指令流的一部分**（顺路带上）；不支持的硬件上是额外一趟 **→ 国产卡跑 MXFP4 必须支持 scaled MFMA 类指令。**
- **上升机制五环**：CSA m=4 → HCA m'=128 ／ Lightning Indexer FP4 ／ **HCA token 强制 4 bit（退化为纯标记）** ／ KV 混合格式（RoPE BF16 + 其余 FP8）／ 权重 FP4 化。
- **★★ HBM 正从"数据层"变成"索引层"**：DeepSeek V4-Pro 1M 上下文仅需 **5.48 GB HBM**（Qwen3-235B 89 GB、GPT-5.5 级 **180+ GB**）；**Keys 留 HBM、Values 卸载到系统内存/SSD/国产 NAND·LPDDR**。→ **B3 的 HBM 需求模型要加"单位 HBM 承载的 token 数"。**
- **硬件缺口不在同一层**：昇腾 950PR 做**数值格式**加速（MXFP8/MXFP4 原生 + 融合 kernel）；中兴论文指的是**压缩注意力索引检索**加速缺失——**后者无人做，是 B6/B7 的空白机会点。**
- **兑换曲线**：精度 ↔ 元数据字节 ↔ GEMM 开销 ↔ 硬件面积。MXFP4 tensor core 面积省 **12%**；Meta OAS+MBS 把 MXFP4/NVFP4 精度差从 10% 压到 <1%，代价 **GEMM +6.2%**。
